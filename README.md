# StrategyLab — система анализа изменений СПР

StrategyLab сравнивает ответы двух версий стратегии системы принятия решений: **BEFORE / MASTER** и **AFTER / BETA**. Приложение показывает, у каких заявок изменились данные, решения и основания, какие блоки затронуты и какие бизнес-проверки сработали.

Область проекта — **модуль 3: приведение и сравнение данных** и **модуль 4: анализ результатов в браузере**. Сбор ретро-заявок и вызов самой СПР находятся за его пределами: на вход поступают готовые ответы JSON/XML.

Документация объединяет инструкции по движку, API, интерфейсу, проверкам, ноутбуку и веб-запуску. Описана консолидированная версия на **8 ноября 2026 года**, включая общую историю отчётов, Sankey/дерево, переходы из проверок и исправления деталей заявок. Для установки актуального репозитория старые архивы и патчи по отдельности не требуются.

## Возможности

- Чтение JSON/XML, поиск пар ответов и диагностика отсутствующих или повреждённых документов.
- Настраиваемая нормализация: пути, исключения, глубина, ключи массивов и бакеты значений.
- Четыре результата сравнения: `SAME`, `VALUE_CHANGED`, `ATTRIBUTE_NEW`, `ATTRIBUTE_LOST`.
- Сохранённые конфигурации и запуск обработки в фоне с журналом этапов, параметрами и исходным кодом.
- Сводный отчёт: изменения решений и оснований, доля одобрений, качество данных и массовые изменения по блокам.
- Настраиваемая веб-сводная с точным подсчётом уникальных заявок и переходом от ячейки к заявке и атрибуту.
- В блоке «Картина изменений» — переключение между Sankey потоков решений и деревом атрибутов.
- Пять стандартных бизнес-проверок, единая таблица результатов и полный список заявок конкретной строки проверки.
- Карточка заявки: решение и основание до/после, наблюдаемые изменения, качество данных и исходные JSON/XML.
- Самостоятельный HTML-протокол со ссылками обратно в приложение.
- Общая история отчётов для вошедших пользователей при личных конфигурациях и правах изменения.
- Доступ к приложению по HTTPS-ссылке с компьютера команды, без установки программ у посетителя.

## Требования и подготовка

Все команды выполняются **из корня репозитория**, если не указано другое. Пути с пробелами заключаются в кавычки. Файлы конфигураций и Python-код сохраняются в UTF-8.

| Компонент | Для чего нужен |
|---|---|
| Git | Получение и обновление исходников |
| Python 3.14 на Windows | Используется `serve.ps1`; указывайте `py -3.14`, чтобы launcher не выбрал другой Python |
| Python 3.11+ для отдельного окружения Linux/Docker | Версия 3.11 используется в Dockerfile и CI; локальные тесты также выполнялись на 3.12 |
| Node.js 22.12+ и npm | Сборка React; Docker и CI используют ветку Node 22 |
| `cloudflared` | Только для временного внешнего HTTPS-доступа через `serve.ps1` |
| Docker / Docker Compose | Дополнительный способ запуска; для Windows-демо не обязателен |

Проверка установленных инструментов на Windows:

```bash
py -3.14 --version
node --version
npm --version
git --version
```

Основные Python-зависимости перечислены в [`requirements.txt`](requirements.txt), фронтенда — в [`frontend/package.json`](frontend/package.json). Исходный рабочий датасет передаётся отдельно; для небольшого воспроизводимого примера есть [`notebooks/demo_data`](notebooks/demo_data).

Получение исходников на новой машине:

```bash
git clone https://github.com/inikita9a-cell/vishnya-balance-pl.git
cd vishnya-balance-pl
```

Используйте согласованную командой версию, содержащую `serve.ps1` и актуальный фронтенд. Дальше выберите один режим: внешний веб-доступ или локальную разработку.

## Веб-доступ с Windows-компьютера

Это основной сценарий демонстрации заказчику: компьютер команды хранит данные и выполняет расчёты, браузер посетителя открывает обычный сайт. FastAPI обслуживает собранный React и `/api` с одного адреса.

### 1. Подготовить данные

Разместите датасет, например, в `D:/SPR/data/RUN-20260827-0001`. Внутри должны быть `RESULTS/BEFORE_MASTER` и `RESULTS/AFTER_BETA`. Путь относится к **компьютеру-серверу**, а не к компьютеру посетителя.

### 2. Установить cloudflared

Скачайте Windows Executable 64-bit с [официальной страницы Cloudflare](https://developers.cloudflare.com/tunnel/downloads/). Сохраните его под точным именем:

```text
.tools/cloudflared.exe
```

Папка `.tools` находится в корне проекта. Это не папка `tools`, содержащая Python-скрипты. В Проводнике включите отображение расширений, чтобы случайно не получить `cloudflared.exe.exe`. Альтернатива — установленный `cloudflared` в `PATH`.

Проверка в Git Bash:

```bash
./.tools/cloudflared.exe --version
```

### 3. Выбрать каталог данных и создать учётные записи

Остановите ранее запущенный API через `Ctrl+C`, затем в Git Bash:

```bash
powershell -ExecutionPolicy Bypass -File ./serve.ps1 -Setup -DataRoot "D:/SPR/data"
```

`DataRoot` — **родитель каталогов RUN**, а не `RESULTS` и не отдельный срез. Скрипт создаёт `.venv-web` на Python 3.14 и устанавливает зависимости, не заменяя старое `.venv`.

В запросе `Account name` введите имя, затем пароль длиной не менее 24 символов. Пустой пароль создаёт случайный и показывает его один раз. При обычном вводе символы пароля не отображаются. Пустое имя завершает добавление и сохраняет настройки.

Создавайте отдельную учётную запись каждому участнику и заказчику. При переходе со старого локального входа используйте прежнее написание имени: `Nikita`, `nikita` и `Никита` — разные владельцы конфигураций.

Повторная настройка добавляет пользователей или меняет пароль введённого имени, сохраняя остальных:

```bash
powershell -ExecutionPolicy Bypass -File ./serve.ps1 -Setup -NoInstall
```

Настройки сохраняются в `.local/web_server.json`: каталог данных, путь к БД и scrypt-хеши паролей. Открытые пароли в этот файл не записываются. Изменения вступают в силу после перезапуска сервера.

### 4. Запустить сайт

Первый запуск:

```bash
powershell -ExecutionPolicy Bypass -File ./serve.ps1
```

Повторный запуск без переустановки зависимостей:

```bash
powershell -ExecutionPolicy Bypass -File ./serve.ps1 -NoInstall
```

Скрипт проверяет порт, собирает фронтенд, поднимает туннель и API, проверяет `/healthz` и выводит:

```text
READY: https://<временный-адрес>.trycloudflare.com
```

Передавайте посетителю адрес **после `READY`** и его персональные данные входа. Браузер запросит логин и пароль. Python, npm и исходный датасет на компьютере посетителя не нужны.

`-NoInstall` пропускает установку Python/npm-зависимостей, но **не сборку фронта**. Для другого порта можно добавить `-Port 8010`.

### 5. Проверить доступ

1. Откройте сайт под своей учётной записью и готовый старый запуск.
2. Откройте тот же адрес в другом браузере или отдельном профиле под второй учёткой. Проверьте общую историю, отчёт, сводную, проверки и карточку заявки.
3. В одном профиле запустите расчёт, во втором продолжайте просматривать готовый отчёт.
4. Проверьте ссылку с телефона через мобильный интернет.
5. Скачайте HTML и проверьте переход обратно на текущий сайт.

### Время жизни ссылки

Quick Tunnel используется для демонстрации: окно сервера, компьютер и интернет должны оставаться включёнными. `Ctrl+C` останавливает API и туннель. После следующего запуска адрес обычно меняется; результаты остаются в БД и `runs/`.

Для постоянного адреса нужен отдельный сервер/хостинг с HTTPS либо именованный туннель и домен. Текущий запуск не устанавливает службу Windows и не обеспечивает автоматический старт после перезагрузки ПК.

## Локальная разработка

Локальный режим предназначен для доверенной команды, в том числе для работы с пользовательским Python-кодом. Для него туннель не нужен.

### Windows

Один раз явно создайте окружение нужной версией Python:

```bash
py -3.14 -m venv .venv
```

Затем:

```bash
powershell -ExecutionPolicy Bypass -File ./run.ps1
```

Скрипт устанавливает зависимости и запускает API с Vite. Только API:

```bash
powershell -ExecutionPolicy Bypass -File ./run.ps1 -BackendOnly
```

Не запускайте `run.ps1` одновременно с `serve.ps1` на одном порту.

### Linux/macOS и ручной запуск

Создайте окружение и установите зависимости:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

API в первом терминале:

```bash
APP_ENV=development REPORT_ACCESS=shared python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Фронтенд во втором терминале:

```bash
cd frontend
npm ci
npm run dev
```

Есть и [`run.sh`](run.sh); он использует `python3` из окружения и запускает процессы совместно. При запуске за пределами доверенного локального окружения учитывайте его сетевые настройки.

| Адрес | Назначение |
|---|---|
| `http://127.0.0.1:5173` | Интерфейс Vite |
| `http://127.0.0.1:8000/docs` | OpenAPI / Swagger |
| `http://127.0.0.1:8000/healthz` | Проверка API и подключения к БД |

Vite перенаправляет `/api` на FastAPI. По умолчанию `VITE_API_BASE_URL` оставляется пустым. Если API работает на другом локальном адресе, задайте `VITE_BACKEND_URL` в окружении Vite. При `serve.ps1` относительный адрес API выставляется автоматически при сборке.

В development вход выполняется по имени через cookie. Этот механизм не подтверждает личность пользователя и не используется для публичного доступа.

## Датасет и конфигурация

### Структура входных данных

```text
data/
  RUN-20260827-0001/
    manifest.json
    RESULTS/
      BEFORE_MASTER/
        <APP_ID>.json
      AFTER_BETA/
        <APP_ID>.json
```

`manifest.json` необязателен. Поддерживаются также `.xml` в пределах адаптера и настроек XML. Имя файла определяет `APP_ID`; отсутствующая сторона пары диагностируется отдельно от отсутствующего атрибута внутри ответа.

Схема и особенности датасета задаются в [`configs/default_spr.yaml`](configs/default_spr.yaml). На новом наборе меняется конфигурация и, при необходимости, пользовательская процедура, а не код ядра.

### Пример основных настроек

```yaml
name: spr_analysis
dataset:
  path: D:/SPR/data/RUN-20260827-0001
  before_dir: RESULTS/BEFORE_MASTER
  after_dir: RESULTS/AFTER_BETA
  formats: [json, xml]
  use_manifest_excludes: true

pool:
  mode: all
  app_ids: []
  filter: null

flatten:
  max_depth: 12
  sep_array_key: "|"
  sep_composite: "+"
  exclude_paths: [appData.request_id, appData.createDateTime]
  include_paths: []
  track_order: false
  auto_key: true
  auto_key_candidates: [id, "*_id", name, code, modelName, action, type]
  arrays:
    "decisionResult.available_offers": {mode: field, key: [product_id, type]}
    "decisionResult.product_trials": {mode: field, key: [product_id]}
    "decisionResult.product_trials.rules": {mode: field, key: [name]}
    "decisionResult.scoring": {mode: field, key: [modelName]}
    "decisionResult.scoring.value": {mode: index}

checks:
  - ar_drop_by_product
  - attribute_new_loss
  - external_score_drift
  - stop_factor_disappeared
  - target_model_changed
check_params: {}
```

Это фрагмент для объяснения параметров. Для первого полного расчёта создавайте конфигурацию **из серверного шаблона**, сохраняющего также `segments`, `quality`, `buckets`, `facts`, `blocks` и остальные правила. Не заменяйте полный шаблон этим сокращённым примером.

| Раздел | Что настраивается |
|---|---|
| `dataset` | Корень набора, относительные пути сторон, форматы, исключения из manifest |
| `pool` | `all`; `list` с точными ID; `filter` по рассчитанным сегментам. Фильтр по сегментам не равен предварительному отбору файлов |
| `flatten` | Глубина, включаемые/исключаемые пути, разделители и сопоставление массивов |
| `xml` | Снятие корневой обёртки, теги элементов массива и приведение типов |
| `serialize` | Строковое представление скаляров |
| `buckets` | Числовые интервалы и исключения по путям; исходные значения сохраняются |
| `segments` | Пути решений, оснований, продуктов, партнёров; группы входных данных и логики |
| `quality` | Обязательные поля и правила наличия основания, включая область отдельного продукта |
| `blocks` | Глубина и включение листьев в агрегаты блоков |
| `facts` | Измерения фактов и включение `ARRAY_KEY` |
| `procedures` | Выбранные обработчики normalize/compare/facts в доверенном режиме |
| `checks`, `check_params` | Набор проверок и их параметры |

Для массива объектов используйте устойчивый ключ. Например, `available_offers` сопоставляется по `product_id + type`, модель — по `modelName`, справочники — по `mfo_id + product_id`. Для числового вектора, где позиция значима, явно задаётся `mode: index`.

Перестановка элементов keyed-массива не должна создавать различия. Отсутствующие или повторяющиеся ключи и переход к позиционному сопоставлению отражаются в диагностике. `max_depth` ограничивает обход; достижение границы диагностируется, а не выдаётся за полный разбор любой глубины.

В публичном режиме все файлы датасета должны находиться внутри выбранного `DataRoot`. В Docker указывается путь **в контейнере**, например `/app/data/RUN-20260827-0001`; Windows-путь `D:/...` внутри Linux-контейнера недоступен.

## Работа в интерфейсе

### 1. Создать конфигурацию и запустить анализ

На вкладке «Настройки» создайте пресет из шаблона, задайте существующий `dataset.path`, проверьте YAML и сохраните конфигурацию. Затем запустите анализ с выбранным пресетом.

Веб-интерфейс использует сохранённые конфигурации. Изменение пресета влияет на новые запуски; уже поставленный в очередь запуск использует свой снимок. API дополнительно поддерживает валидацию YAML, импорт UTF-8 YAML и операции с конфигурациями.

### 2. Посмотреть этапы

На странице запуска отображаются состояние, автор, время, этапы и прогресс. У этапа можно открыть параметры, описание и исходный код. Общий процент отражает ход стадий, а не точную долю оставшегося времени: нормализация может занимать большую часть расчёта.

Обновление страницы не останавливает вычисление. Состояние запуска хранится в SQLite. Аварийная остановка процесса сервера — другой случай: автоматического возобновления фоновой задачи нет.

### 3. Открыть отчёт

Отчёт содержит показатели по заявкам, долю одобрений, матрицы решений и оснований, причины расхождений, блоки и аналитический вердикт.

В «Картине изменений» доступны:

- **Потоки решений** — Sankey: исходное решение → новое решение → состояние основания. Толщина связи — число заявок. Сохранённые решения тоже показаны: «Одобрено → Одобрено» означает, что решение этой группы не изменилось.
- **Дерево атрибутов** — навигация по `PATH`, выбор атрибута, миграции BEFORE/AFTER и страницы связанных заявок. Промежуточные ветки служат навигации; их значения не вычисляются сложением пересекающихся дочерних групп.

Подписи «Сохранено», «Новое», «Не указано» относятся к основанию. В исходных переходах `∅` обозначает неуказанное основание, а не ноль. Полное описание доступно при наведении и в списке потоков. Клик по узлу/связи открывает соответствующие заявки.

Вердикты `REVIEW_REQUIRED`, `INCOMPLETE`, `CHECKS_PENDING`, `NO_CHANGES_OBSERVED` помогают ориентироваться в результате; ни один из них не является автоматическим разрешением на выпуск стратегии.

### 4. Настроить сводную и перейти к деталям

На вкладке сводной выберите строки, колонки и фильтры из фактических измерений запуска. Набор доступных измерений определяется `facts.parquet` и запрашивается у API.

Нажатие на ячейку открывает **уникальные заявки именно этой ячейки**: учитываются общие фильтры и все её измерения, включая `SOURCE` и SQL `null`. Из списка можно открыть заявку и значения конкретного атрибута.

В карточке видны решение и основание до/после, интерпретация наблюдаемых изменений, диагностика качества, `PATH`, ключ массива, значения BEFORE/AFTER и исходные JSON/XML. Большие списки изменений загружаются страницами.

### 5. Прочитать бизнес-проверки

На вкладке «Проверки» результаты всех подключённых проверок собраны в одной таблице. Для стандартных проверок интерфейс использует понятные подписи:

| Исходный результат | Подпись | Смысл |
|---|---|---|
| `FAIL` | Есть сигнал | Найдено изменение или превышен заданный порог; требуется оценка аналитика |
| `PASS` | Сигнал не выявлен | Условие конкретной проверки не сработало |
| `ERROR` | Ошибка выполнения | Проверка не смогла получить корректный результат |

У пользовательских проверок `PASS`/`FAIL` отображаются как «Условие выполнено»/«Условие нарушено». Сами значения `RESULT` в `checks.json` не переписываются. Высокая/низкая уверенность показывается отдельно; наличие сигнала не доказывает ошибочность новой стратегии.

В строке показаны срез, аргумент, количество заявок, знаменатель, метрика и уверенность. **Метрика не всегда равна `CNT / TOTAL`**: в проверке Approval Rate это относительное падение доли одобрений, `(AR_before − AR_after) / AR_before`.

Нажмите на число заявок, затем на нужный ID — откроется полная карточка в реестре того же запуска. Строка идентифицируется через `ROW_ID`, а не только название/аргумент: одинаковые аргументы в BEFORE/AFTER могут соответствовать разным наборам заявок.

`APP_IDS` в файле проверки может содержать лишь примеры. Полный список восстанавливается по `FILTERS`; если это невозможно или число не совпадает с `CNT`, API возвращает диагностическую ошибку. Примеры не выдаются за полный набор.

Кнопка повтора запускает **только проверки** поверх готовых витрин, затем обновляет Summary и HTML. Принятый запрос ещё не означает завершение. Пока задача работает, второй повтор того же запуска отклоняется; обновляйте таблицу после окончания.

### 6. Скачать HTML

HTML-протокол содержит стили и данные внутри файла и открывается без приложения. Переходы из него в онлайн-отчёт и карточки требуют работающего сервера и входа пользователя.

Веб-сервер при скачивании подставляет текущий HTTPS-адрес в поддерживаемые ссылки старых отчётов, не изменяя сохранённый файл. Уже скачанный HTML сам не обновляется: после смены туннеля скачайте его заново. При раздельном локальном запуске адрес UI задаётся `FRONTEND_BASE_URL` или `frontend_base_url` в конфигурации.

## Артефакты и правила подсчёта

| Файл в `runs/<run_id>/` | Содержимое |
|---|---|
| `union.parquet` | Вертикальная нормализованная витрина обеих сторон |
| `comparison.parquet` | Сопоставленные значения и типы изменений |
| `quality.parquet` | Диагностика: заявка, сторона, проблема, путь, детали |
| `segments.parquet` | Одна строка на заявку, решения/основания и полнота сравнения |
| `blocks.parquet` | Изменения по блокам и подблокам |
| `facts.parquet` | Вертикальные агрегированные факты и их измерения |
| `fact_apps.parquet` | Уникальные связи `FACT_ID → APP_ID` |
| `checks.json` | Единый отчёт проверок |
| `summary.json` | Сводка, матрицы, качество и вердикт |
| `report.html` | Экспортируемый протокол |
| `comparison_status.json` | Технические показатели расчёта |
| `procedures_snapshot.json` | Зафиксированные процедуры и настройки исполнения |

Базовые нормализованные колонки: `APP_ID`, `SOURCE`, `PREFIX`, `CLASS`, `SUFFIX`, `ARRAY_KEY`, `KEY`, `PATH`, `DEPTH`, `VALUE`, `ADJUSTED_VALUE`. Ключ сопоставления — **`APP_ID + PATH + ARRAY_KEY`**; `SOURCE` разделяет стороны до сравнения.

`comparison.parquet` — поясняющее сопоставленное представление: `VALUE_BEFORE/AFTER`, `ADJUSTED_BEFORE/AFTER`, `DIFF_FLAG`, `CHANGE_TYPE`. Оно не заменяет вертикальный `union`/`facts`.

| Тип | Значение |
|---|---|
| `SAME` | Сопоставленные значения совпали |
| `VALUE_CHANGED` | Значение существующего атрибута изменилось |
| `ATTRIBUTE_NEW` | Атрибут появился в AFTER |
| `ATTRIBUTE_LOST` | Атрибут отсутствует в AFTER, но был в BEFORE |

Отсутствие атрибута, пустая строка и значение `NULL` различаются. В объяснении заявки сторона имеет `{present, value}`; отсутствие определяется через `present`, а не догадкой по пустому тексту. SQL-пропуски в ответах API передаются как JSON `null`, не как недопустимый `NaN`.

### Точные counts

Сводная считает **`COUNT(DISTINCT APP_ID)`** по членству фактов. `CNT` разных путей, срезов и бакетов **нельзя просто складывать**: одна заявка может входить в несколько групп. Число заявок ячейки должно совпадать с полным distinct-списком после применения её фильтров.

`ATTRIBUTE_NEW` в вертикальных фактах относится к AFTER, `ATTRIBUTE_LOST` — к BEFORE; `SAME` и `VALUE_CHANGED` представлены в обеих сторонах. По умолчанию `ARRAY_KEY` не дробит факты; точные ключи доступны в деталях. Включение `facts.include_array_key` увеличивает детализацию и объём.

В блоках `APPS_TOTAL` — число заявок, в которых есть этот блок, а не обязательно весь датасет. `SHARE = APPS_CHANGED / APPS_TOTAL`; разные блоки могут пересекаться.

### Качество и интерпретация

Диагностируются, в частности, `PARSE_ERROR`, `APP_MISSING_BEFORE/AFTER`, `REQUIRED_FIELD_MISSING`, `DECISION_WITHOUT_REASON`, `DUPLICATE_KEY`, `ARRAY_KEY_MISSING`, `ARRAY_KEY_FALLBACK`, `DEPTH_TRUNCATED`.

Пропавшая сторона заявки делает сравнение неполным. Наблюдаемые односторонние строки сохраняются, но не должны интерпретироваться как подтверждённая потеря атрибутов в полной паре. Отсутствующее основание не выдумывается.

`CAUSE=LOGIC/INPUT_DATA/BOTH/NONE` определяется по группам путей в конфигурации. Это классификация наблюдаемых различий, **не доказательство причинно-следственной связи** и не признак «ожидаемости» изменения.

## Пользовательские процедуры и проверки

Исполнение собственного Python доступно **только в доверенном development-режиме**. Публичный staging допускает стандартный пайплайн и пять встроенных проверок; произвольные workspace/file-процедуры, overrides и неизвестные проверки блокируются.

Subprocess и таймаут ограничивают время исполнения, но не изолируют код от файлов, сети и окружения процесса. Не открывайте development-сервер с произвольным Python для внешних посетителей.

### Выбор обработчиков

Процедуры сохраняются через `/api/procedures`, после чего их ID указываются в YAML:

```yaml
procedures:
  normalize: {procedure_id: 12, entry: normalize, params: {}, timeout_seconds: 120}
  compare: {procedure_id: 13, entry: compare, params: {}, timeout_seconds: 120}
  facts: {procedure_id: 14, entry: facts, params: {}, timeout_seconds: 120}
```

ID здесь условные — замените их на свои. Также поддерживаются явные `source: workspace` с `code` и `source: file` с `path`. Невыбранный этап выполняется встроенным обработчиком.

| Вид | Контракт |
|---|---|
| normalize | `normalize(before, after, cfg, params, app_id, issues)` → `(before_rows, after_rows)` |
| compare | `compare(union_df, cfg, params, issues)` → DataFrame схемы comparison |
| facts | `facts(comparison, segments, cfg, params)` → `(facts_df, fact_apps_df)` |
| check | `check(mart, params)` или официальный `CHECK` → список строк отчёта |

Проверяются схема, ключи, принадлежность строк заявке/стороне, типы изменений и соответствие counts связям фактов. Рабочие небольшие примеры — [`examples/p0_03`](examples/p0_03).

При постановке запуска в очередь сохраняются исходник, параметры и SHA-256. Позднее редактирование `.py`, записи Procedure или конфигурации не подменяет код уже запущенного расчёта.

Текущий интерфейс настроек предоставляет YAML и каталоги. Программное создание, подключение и пробное выполнение процедур описаны API ниже; встроенного полноценного Python IDE в этом интерфейсе нет. Для пошаговой интерактивной работы предусмотрен Jupyter Notebook.

### Пять встроенных проверок

| ID | Что проверяет |
|---|---|
| `ar_drop_by_product` | Относительное снижение Approval Rate по продукту относительно порога |
| `attribute_new_loss` | Появление/исчезновение атрибутов и долю затронутых заявок |
| `external_score_drift` | Изменение внешнего скора и расхождение предиктора со значением источника |
| `stop_factor_disappeared` | Исчезновение стоп-фактора или прекращение его срабатывания |
| `target_model_changed` | Изменение целевой модели решения |

Исходники и значения параметров по умолчанию находятся в [`procedures/checks`](procedures/checks). Например, стандартный `max_drop_rel` для Approval Rate равен `0.10`; изменить его можно через `check_params.ar_drop_by_product`. Порог применяется к относительному падению, не к процентным пунктам.

### Пример своей проверки

Учебная проверка, сигнализирующая о наличии любых различий:

```python
def check(mart, params):
    apps = sorted(mart.app_ids(diff_flag=1))
    total = mart.total_apps()
    return [{
        "LABEL": "Есть изменения атрибутов",
        "SOURCE": "AFTER",
        "ARGUMENT": "Все изменённые атрибуты",
        "CNT": len(apps),
        "TOTAL": total,
        "METRIC": len(apps) / total if total else 0.0,
        "RESULT": "FAIL" if apps else "PASS",
        "CONFIDENCE": "HIGH",
        "APP_IDS": apps[:20],
        "FILTERS": {"app_ids": apps},
    }]
```

Это пример контракта, а не критерий допустимости релиза. `MartAPI` предоставляет `rows(**filters)`, `count(**filters)`, `app_ids(**filters)`, `segments()` и `total_apps()`. `count` считает строки, `app_ids` — уникальные заявки.

Сохраните процедуру с `kind: check`, затем подключите её через `/api/procedures/{pid}/attach` или добавьте спецификацию в `checks`. `check_params[id]` имеет приоритет над параметрами процедуры.

Для пробного выполнения используйте `/api/procedures/{pid}/try` с `config_id` и 1–3 `app_ids`. Для обновления проверок готового запуска отправьте `POST /api/runs/{rid}/checks/rerun` с `config_id`, дождитесь `done` через endpoint задачи, затем перечитайте результаты. Без `config_id` используется ранее зафиксированный набор, а не автоматически изменённая конфигурация.

Повтор проверок не перечитывает исходный датасет и не меняет Parquet. Новая ревизия проверок хранится отдельно от исходного снимка запуска. Повторная отправка во время работающей задачи возвращает `409`.

| Метод и путь относительно `/api/runs/{rid}` | Назначение |
|---|---|

Например, ячейка сводной:

```json
{
  "rows": ["PATH"],
  "cols": ["CHANGE_TYPE"],
  "filters": {"DIFF_FLAG": 1, "SOURCE": "AFTER (BETA)"}
}
```

При переходе из неё в `/pivot/apps` передаются и эти общие фильтры, и точные значения `PATH`/`CHANGE_TYPE` нажатой ячейки. SQL `null` передаётся как JSON `null`, не строка `"NULL"`.

Типовые статусы: `401` — нужен вход; `403` — запрещённая операция/неверный origin; `404` — ресурс не найден или недоступен владельцу; `409` — конфликт задачи либо недоступность артефактов; `422` — ошибка данных/контракта запроса. В staging меняющие запросы требуют `Origin`, совпадающий с `APP_BASE_URL`; проверенной личности из cookie или произвольного заголовка недостаточно.

./.venv-web/Scripts/python.exe -m engine.run_comparison --dataset "D:/SPR/data/RUN-20260827-0001" --out runs/cli_parts_01
./.venv-web/Scripts/python.exe -m engine.run_checks --run runs/cli_parts_01

`engine.pipeline` включает проверки, Summary и HTML; `engine.run_comparison` не заменяет полный серверный запуск. Каталог, созданный CLI, сам по себе **не регистрируется в SQLite**: он не появится автоматически в истории UI, и ссылки на него не создают серверную запись. Для пользовательского сценария запускайте через API/интерфейс.

### Проверить, что ускорение не потеряло данные

```bash
./.venv-web/Scripts/python.exe tools/compare_run_results.py runs/RUN_BEFORE runs/RUN_AFTER --db db/app.db > run_comparison.json
```

Замените `runs/RUN_BEFORE` и `runs/RUN_AFTER` на пути к двум реальным запускам. Сравнение читает результаты и не меняет их. Проверяются таблицы, аналитические поля проверок, конфигурации и снимки; изменяющиеся служебные поля времени не считаются различием расчёта. `PASS` подтверждает совпадение проверяемого содержимого, `FAIL` — различие, `INCOMPLETE` — нехватку данных для вывода. Само ускорение без такой сверки не доказывает сохранение полноты.

### Ручной сценарий демонстрации

1. Войти, создать конфигурацию из шаблона и запустить анализ.
2. Во время расчёта открыть этап и его код; вторым пользователем открыть готовый отчёт.
3. После `done` сверить итоговые числа и диагностику качества.
4. Перестроить сводную в двух раскладках, применить фильтр, открыть ячейку и сверить количество уникальных ID.
5. Открыть заявку и конкретный атрибут BEFORE/AFTER; отдельно показать сохранённое решение с изменёнными данными.
6. Переключить Sankey/дерево, открыть связанный набор заявок.
7. Из строки проверки перейти к точной заявке; показать различие сигнала и ошибки выполнения.
8. Для демонстрации своего Python использовать доверенный локальный режим: добавить проверку и повторить только проверки.
9. Скачать HTML, открыть локально и перейти обратно в отчёт/карточку.
10. Обновить страницу и проверить сохранность результата.

## Docker и CI

В репозитории есть **два разных варианта**, их настройки не следует смешивать.

### Docker Compose для разработки

[`docker-compose.yml`](docker-compose.yml) запускает backend из `Dockerfile.backend` и отдельный nginx-фронтенд из `frontend/Dockerfile`:

```bash
docker compose up --build
```

Интерфейс — порт `5173`, API — `8000`. По умолчанию монтируется `./data`; другой каталог с RUN-подкаталогами задаётся `DATASET_HOST_DIR`. В YAML используется `/app/data/<RUN>`.

Результаты лежат в примонтированном `./runs`, БД — в volume `app_db` по `/app/db/app.db`. Это **другая БД**, не локальная `./db/app.db`. На Linux каталог результатов должен быть доступен пользователю контейнера с UID 1000. Текущий Compose — development-вариант; не публикуйте его порты в интернет как замену защищённому веб-запуску.

### Один staging-образ

Корневой [`Dockerfile`](Dockerfile) собирает React и API в один образ:

```bash
docker build -t strategylab:staging .
```

Для развёртывания требуются HTTPS перед приложением, постоянное хранилище и персональные учётные записи. Основные настройки:

| Переменная/каталог | Назначение |
|---|---|
| `APP_ENV=staging` | Защищённый внешний режим |
| `APP_BASE_URL` | Точный внешний HTTPS origin; без пути и query |
| `STAGING_USERS_JSON` | JSON имён и scrypt-хешей, передаваемый как секрет окружения |
| `REPORT_ACCESS=shared` | Общая история; задаётся явно |
| `DB_DIR` | По умолчанию образа `/var/lib/strategylab/db` |
| `STATIC_DIR` | В образе `/app/static` |
| `/var/lib/strategylab/runs` | Постоянные результаты; связан с `/app/runs` |
| `/var/lib/strategylab/data` | Входные наборы; связан с `/app/data` |

Необходимые записи хешей можно подготовить локально через [`scripts/staging_credentials.py`](scripts/staging_credentials.py); при нескольких пользователях объедините записи в один JSON. Секреты не передаются в `VITE_*`, Docker ARG или Git. Не копируйте локальную БД поверх существующей серверной без отдельного плана переноса.

Без корректной настройки публичной авторизации приложение возвращает `503`, кроме `/healthz`. До передачи ссылки проверьте входы, общую историю, запрет изменения чужих данных, сохранность одного и того же запуска после redeploy и резервное копирование. Автоматически созданного облачного сервиса в составе репозитория нет.

### CI

Workflow в [`.github/workflows/ci.yml`](.github/workflows/ci.yml) выполняет Python-тесты, тесты/сборку фронта, сборку Docker и контейнерный smoke-тест. В текущем YAML он запускается для pull request и push в `develop` / `demo/strategylab-staging`; push в `main` сам по себе не гарантирует его выполнение. Проверяйте фактический статус Actions для нужного коммита.

## Хранение, резервное копирование и обновление

| Путь | Что сохранять |
|---|---|
| `db/` или выбранный `DB_DIR` | SQLite с пользователями, конфигурациями, запусками и журналом |
| `runs/` | Витрины, проверки, отчёты, снимки и состояния задач |
| `.local/` | Настройки веб-сервера и хеши паролей; хранить конфиденциально |
| Внешний каталог данных | Оригинальные JSON/XML и manifest |
| `configs/`, `procedures/` | Версионируемые шаблоны и доверенные файлы процедур |

Часть исходных ответов может читаться по пути из снимка конфигурации. Для доступности старых карточек сохраняйте исходный датасет и его расположение либо планируйте контролируемый перенос.

Перед резервным копированием дождитесь окончания задач и остановите сервер. Сохраняйте БД и результаты **вместе**, а также `.local` и исходные данные. Копирование только `app.db` во время работы WAL не является гарантированным согласованным снимком; для online-копии нужен штатный механизм backup SQLite.

Для обновления: завершите задачи, сохраните изменения, остановите сервер, получите согласованную версию Git, выполните тесты и сборку, затем запустите сервер. Если коллеги изменили те же файлы, разрешите конфликты до запуска. Не заменяйте текущие исходники целиком файлами из старых архивов.

В Git не добавляются датасеты, `runs/`, SQLite, `.local`, `.tools`, виртуальные окружения и секреты. Добавление ещё одного `.md` не требует перезапуска приложения. Изменения backend требуют перезапуска; изменения frontend — новой сборки.

## Диагностика

| Симптом | Что проверить |
|---|---|
| `No module named pytest` | Используется другой Python. Запускайте тесты через `.venv-web/Scripts/python.exe` или явно `py -3.14` с установленными зависимостями |
| `node/npm: command not found` | Установка Node/npm и `PATH`; после установки откройте новый терминал |
| `cloudflared not found` | Точный путь `.tools/cloudflared.exe`, отсутствие двойного `.exe`, либо установленный бинарник в `PATH` |
| `Port 8000 is busy` | Остановите прежний API или задайте `serve.ps1 -Port 8010` |
| `Dataset path does not exist` | Путь в сохранённом пресете относится к серверу; `dataset.path` должен вести к RUN, а `DataRoot` — к его родителю |
| Другой пользователь не видит историю | `REPORT_ACCESS`, актуальный процесс API и используемая БД; Docker volume и локальная БД различаются |
| Не переключается учётка на публичной ссылке | Браузер кеширует Basic-вход; используйте отдельный профиль/браузер |
| История общая, но нет старых конфигураций | Конфигурации личные; проверьте точное имя владельца, регистр и алфавит |
| `409` при повторе проверок | Уже есть работающая задача; дождитесь завершения и обновите таблицу |
| `422` при раскрытии строки проверки | Нужен точный `ROW_ID`; проверьте полноту `APP_IDS`, `FILTERS` и соответствие `CNT` |
| 500 при открытии заявки | Сохраните traceback из окна API, `run_id` и `APP_ID`. Ошибка загрузки не доказывает отсутствие различий; не подменяйте её пустой таблицей |
| Прогресс долго меняется на одном этапе | Общий процент не равен времени; посмотрите текущую стадию и её прогресс |
| Ускорение в несколько раз | Сверьте конфигурации, пулы и содержимое результатов через `compare_run_results.py` |
| Старый HTML ведёт на неработающий адрес | После смены туннеля скачайте отчёт заново с текущего сайта |
| `UnicodeDecodeError` на Windows | Явно читайте JSON/YAML как UTF-8; `checks.json` и конфиги не следует читать через системную cp1251 |
| Предупреждения `utcnow`, `on_event`, TestClient | Это deprecation warnings; оценивайте финальный статус тестов. Они не равнозначны ошибке кодировки |
| Git показывает `(END)` | Это pager списка изменений; английская `q` возвращает в терминал |

## Границы реализации и развитие

- Проверены два одновременных реальных расчёта с разными пулами и чтение третьим пользователем. Это не нагрузочный тест на сотни клиентов или подтверждение всех порогов для 20 000 заявок.
- Сервер запускается с одним Uvicorn worker. Перезапуск страницы поддерживается; автоматическое восстановление вычисления после остановки процесса или ПК не реализовано. Не увеличивайте число worker-процессов без проверки координации задач.
- Для данных действует настраиваемый контракт JSON/XML и ограничение глубины. Поддержка произвольного документа любой структуры без конфигурации не заявляется.
- Основной реестр загружает список сегментов и часть фильтров применяет в браузере; серверная пагинация есть в pivot apps, Explorer и объяснениях. Масштабирование общего реестра — отдельная задача.
- Повтор проверок имеет API статуса и защиту от дублирования, но текущая кнопка интерфейса требует обновления таблицы после завершения. Сквозной редактор Python с автоматическим сопровождением задачи остаётся развитием UI.
- Агрегаты блоков есть; универсальный переход из любого блока в произвольный фильтр реестра не заявляется. Для детализации используйте дерево и сводную по атрибутам.
- API импорта YAML не является загрузкой исходного датасета. Данные текущего веб-запуска размещаются на сервере отдельно.
- «Ожидаемые / неожиданные изменения» требуют согласованных правил заказчика. Нельзя подменять их `PASS/FAIL` или `CAUSE`.
- В [`engine/llm.py`](engine/llm.py) есть опциональный клиент OpenAI-совместимого API, но стандартный `engine.pipeline` не вызывает его автоматически. Наличие ключа `LLM_API_KEY` само по себе не добавляет «мнение ИИ» в отчёт. Это отдельная интеграция, а не обязательная часть текущего запуска.
- Временный туннель не заменяет постоянный домен, службу, мониторинг, восстановление и проверенный production-деплой.

README описывает фактическую реализацию, а не объявляет выполненными все пункты исторического аудита. При противоречиях приоритет имеют актуальные требования заказчика и согласованные уточнения; старые планы, промежуточные README и число тестов в них не являются доказательством готовности текущего коммита.
