# P0-04 — своя проверка и повтор без нормализации

Требуется установленный P0-03. Распаковать весь ZIP в корень репозитория.
Остановить API. `backend/` передан патчем; остальные файлы готовы к использованию.

```bash
git apply --ignore-space-change --check P0_04_backend.patch
git apply --ignore-space-change P0_04_backend.patch
py -m pytest tests/test_check_jobs.py -q
py tools/p0_04_smoke.py
```

Если `--check` упал, остановиться и прислать вывод; повторно применённый
патч тоже выдаёт эту ошибку. После установки перезапустить API.
Ожидается `13 passed` и `P0-04 OK`. Общий прогон: `py -m pytest tests -q`.
Новых зависимостей и миграций БД нет.

## Контракт для фронтера

1. Сохранить код: существующий `POST /api/procedures` с
   `{kind: "check", source: "workspace", code: "..."}` → `{id}`.
   Формат кода: `check(mart, params) -> list[dict]` либо официальный `CHECK`.
2. Проверить черновик: существующий `POST /api/procedures/{pid}/try` с
   `{config_id, app_ids: ["APP_ID"], code, params}` → `{ok, result}` (P0-03).
3. Подключить к конфигу: **`POST /api/procedures/{pid}/attach`** с
   `{config_id, check_id: "my_check", params: {}, label?: "Название", entry?: "check"}`.
   Остальные проверки сохраняются. Повторный attach того же check_id обновляет
   выбранную процедуру, а не создаёт дубликат.
4. Повторить: **`POST /api/runs/{rid}/checks/rerun`** с `{config_id}`.
   Ответ: `{ok: true, job_id, status: "queued", progress, check_ids, ...}`.
   `ok` означает постановку в очередь, ещё не готовый результат.
5. Опрос раз в секунду: **`GET /api/runs/{rid}/checks/jobs/{job_id}`**.
   Статусы: `queued | running | done | failed`; есть `stage`, `progress`,
   `error`, `counts: {pass, fail, error}` после успешного завершения.
   До терминального статуса кнопка повтора заблокирована.
6. Только после `done` перечитать `GET /api/runs/{rid}/checks` и обновить таблицу.
   Сводка и `/report.html` уже пересозданы. При `failed` показать `error`;
   прежний опубликованный отчёт сохранён.
7. После F5: **`GET /api/runs/{rid}/checks/status`** → `{job: {...} | null}`,
   затем продолжить опрос незавершённой задачи.

У `/rerun` также допустимы `{checks: [...], check_params: {...}}` вместо
config_id — для явного набора. Без тела повторяется последняя успешно
опубликованная версия проверок, а при её отсутствии — снимок исходного запуска.
Если нужно применить изменения текущего конфига, обязательно передать config_id.
Набор `checks: []` действительно отключает проверки, не заменяется стандартным.

## Что проверено

- Полный REST-путь: создать → проверить → подключить → запустить → дождаться.
- Своя строка рядом с пятью выданными; PASS/FAIL/ERROR, CNT/TOTAL, APP_IDS.
- Код/контракт одной проверки может упасть; остальные продолжаются.
- Не читается исходный датасет, не меняются Parquet и исходный Run.config_snapshot.
- Из другого конфига берутся только checks/params/overrides, а не новый dataset.
- Исходники и параметры фиксируются при постановке задачи; StageLog содержит
  фактически исполненные проверки. Новая ревизия хранится отдельно от исходного запуска.
- При сбое расчёта/HTML сохраняются старые опубликованные файлы; при ошибке
  публикации выполняется откат уже заменённых файлов.
- Два одновременных повтора одного запуска получают 409; другой пользователь — 404.

Расчёт идёт в фоновом потоке текущего API, как раньше. Статус задачи сохранён
на диске; перезапуск процесса не возобновляет вычисление. При прерванном процессе
может остаться `.checks-rerun.lock`; удалять его можно только после остановки API
и проверки, что задача больше не исполняется. Защита от аварии процесса ровно
во время публикации нескольких файлов не является транзакцией файловой системы.

Фронтенд в ZIP не менялся. Для полного закрытия P0-04 фронтеру нужно подключить
редактор и шаги 1–7; прежняя кнопка «Повторить проверки» сама статус не опрашивает.
