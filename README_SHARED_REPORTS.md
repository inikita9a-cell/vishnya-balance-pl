# Общая история отчётов и проверка полноты расчёта

Патч поверх `36d1f08` с уже применёнными LOCAL_36D1F08_FIX и UNICODE_UI_FIX. Соответствует уточнению пользователя: вошедшие участники видят отчёты друг друга.

## Политика доступа

- `REPORT_ACCESS=shared`: общий список запусков, детали/этапы, отчёты, проверки, заявки, исходники, объяснения и аналитические запросы доступны вошедшим пользователям независимо от автора. Старые записи сразу видны; миграция БД и перенос владельцев не нужны.
- Конфиги, процедуры и запуск/пересчёт чужого результата остаются у владельца. Просмотр не даёт права изменения.
- Без входа отчёты не выдаются.
- `REPORT_ACCESS=private` или отсутствие переменной при ручном старте API сохраняет прежний приватный режим.
- `run.ps1` и `run.sh` для development по умолчанию включают `shared`, если режим не задан явно. Для staging автоматическое включение не добавляется.

Это осознанная замена прежнего поведения P0-09 для локальной команды по уточнению пользователя. Приватный режим и его тесты сохранены. Доступы конфигов не смешиваются с видимостью отчётов.

## Применить

Распакуй ZIP в корень. В нём патч существующих файлов, новый инструмент сравнения и два файла тестов.

```bash
git apply --ignore-space-change --check SHARED_REPORTS.patch
git apply --ignore-space-change SHARED_REPORTS.patch
py -m pytest tests/test_shared_reports.py tests/test_compare_run_results.py -q
```

При ошибке `--check` остановиться: могли прийти изменения команды, особенно в `check_apps_api.py`. Не заменять её файл старой версией целиком. Патч меняет в этом файле только функцию проверки доступа.

После применения останови старый сервер Ctrl+C и запусти заново:

```bash
powershell -ExecutionPolicy Bypass -File ./run.ps1
```

Обнови страницу браузера и войди другим именем. История должна содержать прежние запуски и их настоящих авторов. Если история пуста, проверь, что запущен именно обновлённый API и та же БД: локальная `db/app.db` и Docker volume — разные хранилища.

Для ручного API-старта из Git Bash:

```bash
REPORT_ACCESS=shared py -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Конфиги нового пользователя по-прежнему отдельные; чужая конфигурация не становится его редактируемым пресетом только из-за общего отчёта.

## Проверить, что ускорение не связано с потерей данных

На скринах показаны два завершённых запуска:

- Прежний: `8bc1c03dea54`; сумма длительностей этапов около 155 с, нормализация 129 с.
- Новый: `3ee8c38ec741`; нормализация 26,7 с. Сам скрин этапов не показывает количество обработанных заявок и атрибутов.

Предыдущий UNICODE_UI_FIX менял авторизацию и UI-ошибки, не алгоритм расчёта и не выбор проверок. Изменение скорости само по себе не доказывает ни потерю данных, ни её отсутствие. Причина ускорения пока не установлена.

Из корня выполни read-only сравнение:

```bash
py tools/compare_run_results.py runs/8bc1c03dea54 runs/3ee8c38ec741 --db db/app.db > run_comparison.json
```

После завершения пришли `run_comparison.json`. Исходные файлы/БД/результаты не меняются. Сам протокол содержит числа, признаки совпадения и количество добавленных/исчезнувших строк, без значений исходных ответов СПР. Время сравнения не относится к времени самого расчёта.

### Что сравнивается

1. Все строки и колонки `union`, `comparison`, `quality`, `segments`, `blocks`, `facts`, `fact_apps`: число строк, схема и мультимножество содержимого с SHA-256 каждой канонической строки. Порядок строк игнорируется, дубликаты учитываются.
2. Все строки `checks.json` и их содержимое, включая CHECK_ID, CNT/TOTAL, метрику, результат и APP_IDS. Игнорируются только время исполнения и traceback.
3. Полный `procedures_snapshot.json`.
4. `summary.json`, за исключением run_id и времени построения summary. Отдельно выведены количества заявок, неполных пар, строк сравнения и различий.
5. YAML snapshot обоих запусков из SQLite (без служебного `_meta`) и исходные записи этапов: одинаковый набор, успешный статус, код и параметры. Повторные записи rerun не подменяют первую запись исходного этапа.

Не сравнивается HTML-текст, содержащий разные run_id. Инструмент не перечитывает и не пересчитывает исходный датасет. Он доказывает эквивалентность сохранённых результатов и доступных снимков, а не неизменность исходных файлов в прошлые моменты времени.

### Как читать результат

- `status: PASS` — проверяемые артефакты, конфиг и исполненные этапы совпали; оба запуска завершены. Существенное сокращение строк/проверок не скрывается за теми же итоговыми счётчиками.
- `status: FAIL` — есть различия либо незавершённость/несовпадение исполнения. Это повод посмотреть конкретный раздел, а не автоматическое доказательство ошибки: например, легитимное изменение конфигурации или rerun проверок тоже меняет результат.
- `status: INCOMPLETE` — результаты совпали, но нет достаточной метаинформации из указанной БД. Проверка не считается пройденной.

Коды возврата: 0 / 1 / 2 соответственно. Если файл результата пуст, пришли текст ошибки терминала: возможен неверный ID/путь либо отсутствие зависимостей в выбранном Python.

Если проверки после одного запуска пересчитывали с иным составом, `checks.json` может отличаться при одинаковом исходном расчёте. Утилита честно отметит различие; сравнивать лучше два запуска с одинаковыми настройками и без промежуточной смены проверок.

## Проверено в пакете

Полный Python-прогон: **272 passed**. Для `run.sh` дополнительно проверен синтаксис Bash; файл приведён к LF. Фронтенд этим пакетом не изменяется.

Новые тесты покрывают общую историю и чтение старого отчёта новым пользователем, read-only POST аналитики, сохранение владельца для изменений, отсутствие анонимного доступа. Тесты сравнения проверяют перестановку строк, изменение только времени, незаметное в summary удаление атрибута, отсутствие доказательств и смену конфига.

Полный пользовательский Windows-датасет здесь недоступен: сравнение двух указанных запусков нужно выполнить на компьютере пользователя. Общий браузерный сценарий нового режима также проверяется после перезапуска у пользователя.
