# StrategyLab — система анализа изменений СПР

StrategyLab — веб-приложение для сравнения результатов **двух версий стратегии системы принятия решений (СПР)**: `BEFORE (MASTER)` и `AFTER (BETA)`. Приложение нормализует ответы JSON/XML, выявляет изменения по заявкам и атрибутам, выполняет автоматические проверки, строит сводные отчёты и позволяет перейти от агрегированных показателей к конкретной заявке. Отчёт доступен в браузере и выгружается в HTML.

> **Для экспертов хакатона.** Проект запускается **локально на вашей машине**, без доступа к ноутбуку команды, облачному серверу или внешней демонстрационной ссылке. Основной способ — Docker Compose. Ниже также описан запуск без Docker. В репозитории есть небольшой публичный демонстрационный датасет для проверки решения; полный датасет организаторов подключается отдельно.

## 1. Требования к окружению

**Рекомендуемый вариант:** Windows 10/11, Linux или macOS с установленными:

- [Git](https://git-scm.com/downloads) — для клонирования исходного кода;
- [Docker Desktop](https://www.docker.com/products/docker-desktop/) (Windows/macOS) или Docker Engine с **Docker Compose v2** (Linux) — для сборки и запуска двух сервисов;
- доступом к интернету при первоначальной установке зависимостей и Docker-образов.

Проверка инструментов:

```bash
git --version
docker --version
docker compose version
```

Для запуска **без Docker** нужны **Python 3.11** (с `venv` и `pip`) и **Node.js 22** (с `npm`). Именно эти версии используются в Dockerfile. На Windows также нужен Python Launcher (`py`), поскольку его использует `run.ps1`.

Для Docker рекомендуется выделить не менее **4 ГБ оперативной памяти**; это рекомендация для комфортного запуска, а не измеренный минимальный порог.

## 2. Быстрый запуск с нуля (Docker Compose)

### Шаг 1. Получить исходный код

В терминале (PowerShell, Terminal или bash):

```bash
git clone https://github.com/inikita9a-cell/vishnya-balance-pl.git
cd vishnya-balance-pl
```

Все следующие команды выполняются **из корня репозитория** — папки, где находится `docker-compose.yml`.

### Шаг 2. Подготовить демонстрационные данные

В репозитории есть `notebooks/demo_data`: 4 пары JSON-ответов со структурой, совместимой с движком. Чтобы данные были доступны контейнеру, скопируйте их в папку `data/`.

**Windows / PowerShell:**

```powershell
New-Item -ItemType Directory -Force data, runs | Out-Null
Copy-Item -Path .\notebooks\demo_data -Destination .\data\RUN-DEMO-0001 -Recurse -Force
```

**Linux / macOS / bash:**

```bash
mkdir -p data runs
cp -R notebooks/demo_data data/RUN-DEMO-0001
```

На **Linux** при ошибке `Permission denied` во время записи результатов в `runs/` выдайте право записи UID 1000 (пользователь контейнера):

```bash
sudo chown -R 1000:1000 runs
```

Каталог `data/` и результаты `runs/` не включаются в Git. Оригинальные файлы ответов не изменяются.

### Шаг 3. Собрать и запустить приложение

```bash
docker compose up --build -d
```

При первом запуске Docker загрузит необходимые базовые образы, установит Python- и npm-зависимости и соберёт фронтенд. Проверьте состояние:

```bash
docker compose ps
docker compose logs --tail=50 backend
```

Адреса на **той же машине**, где запущен Docker:

| Компонент | Адрес |
| --- | --- |
| **Веб-интерфейс StrategyLab** | **http://localhost:5173** |
| Проверка работоспособности API | http://localhost:8000/healthz |
| Интерактивная документация REST API (Swagger) | http://localhost:8000/docs |

Для `/healthz` ожидается JSON со статусом `"ok"`. Бэкенд — FastAPI на порту `8000`, фронтенд — собранный React, который раздаёт Nginx на порту `5173`. Запросы `/api/` проксируются на бэкенд; отдельная настройка CORS в браузере не требуется.

### Шаг 4. Создать и запустить первый анализ в интерфейсе

1. Откройте **http://localhost:5173** и войдите под произвольным локальным именем.
2. Перейдите в раздел **«Конфигурации»** и нажмите **«Создать из шаблона»**.
3. В YAML-параметрах замените значение `dataset.path` на `data/RUN-DEMO-0001`. Пути срезов уже заданы в шаблоне; в результате блок должен выглядеть так:

   ```yaml
   dataset:
     path: data/RUN-DEMO-0001
     before_dir: RESULTS/BEFORE_MASTER
     after_dir: RESULTS/AFTER_BETA
     formats: [json, xml]
   ```

4. Чтобы ссылки из скачанного HTML вели обратно в локальный интерфейс, добавьте **на верхнем уровне YAML** (не внутри `dataset`):

   ```yaml
   frontend_base_url: http://localhost:5173
   ```

5. Сохраните конфигурацию, затем выберите **«Запустить с пресетом»**.
6. Дождитесь завершения обработки в разделе запусков; откройте сравнительный отчёт, реестр заявок и проверки. Проверьте переход от агрегированных чисел к списку заявок и конкретным значениям `BEFORE/AFTER`. Откройте или сохраните HTML-отчёт.

**Контроль для демонабора:** 4 заявки, 3 заявки с различиями, 2 заявки со сменой решения (результат сохранённого локального smoke-теста). Демонабор не заменяет проверку на полном датасете организаторов.

### Шаг 5. Остановить приложение

```bash
docker compose down
```

Повторный запуск: `docker compose up -d`. SQLite хранится в Docker volume `app_db`, результаты — в папке `runs/`, исходные датасеты — в папке `data/`. Для полного удаления **Docker-базы** можно использовать `docker compose down -v`, но это удалит сохранённые в ней записи пользователей, конфигураций и запусков. Не применяйте `-v`, если данные нужны.

## 3. Полный датасет организаторов

Для воспроизведения анализа на полном прогоне нужен датасет **`RUN-20260827-0001`** из материалов хакатона. Он **не включён в GitHub-репозиторий**; при необходимости запросите исходный набор у организаторов. Это отдельный входной артефакт, а не внешняя служба.

Поместите датасет в следующую структуру **относительно корня репозитория**:

```text
data/
└── RUN-20260827-0001/
    ├── manifest.json
    └── RESULTS/
        ├── BEFORE_MASTER/
        │   ├── <APP_ID_1>.json
        │   └── ...
        └── AFTER_BETA/
            ├── <APP_ID_1>.json
            └── ...
```

По официальному заданию открытый прогон включает **2002 заявки и 4004 JSON-ответа** (по два на заявку). Датасет содержит ответы СПР, а не исходный код её стратегии.

При выборе **«Создать из шаблона»** конфигурация `configs/default_spr.yaml` уже содержит путь:

```yaml
dataset:
  path: data/RUN-20260827-0001
  before_dir: RESULTS/BEFORE_MASTER
  after_dir: RESULTS/AFTER_BETA
```

Сохраните такой пресет и запустите анализ. Контейнер видит `./data` как `/app/data`, поэтому **Windows-путь вида `C:\...` не следует указывать в YAML внутри Docker**. При стандартном расположении используйте именно `data/RUN-20260827-0001`.

**Если датасет уже хранится в другом каталоге**, вместо копирования можно указать папку, содержащую `RUN-20260827-0001`, через переменную `DATASET_HOST_DIR` **до** `docker compose up`:

```powershell
# Windows / PowerShell (пример)
$env:DATASET_HOST_DIR = 'D:\datasets'
docker compose up --build -d
```

```bash
# Linux/macOS (пример)
DATASET_HOST_DIR=/home/user/datasets docker compose up --build -d
```

При таком подключении `dataset.path` в YAML **не меняется**: внутри контейнера это всё равно `data/RUN-20260827-0001`. Если вы ранее запускали Compose с другим томом данных, пересоздайте контейнер командой `docker compose up -d --force-recreate` с новой переменной.

## 4. Дополнительная проверка движка из терминала

Можно воспроизвести расчёт **без браузера**, вызвав тот же движок `engine.pipeline`, который использует FastAPI:

```bash
docker compose exec backend python -m engine.pipeline --dataset /app/data/RUN-DEMO-0001 --out /app/runs/manual_demo
```

Для полного набора замените `/app/data/RUN-DEMO-0001` на `/app/data/RUN-20260827-0001` и укажите **новую** папку после `--out`.

После успешного завершения в `runs/manual_demo/` появятся, в частности:

```text
union.parquet
comparison.parquet
segments.parquet
blocks.parquet
facts.parquet
fact_apps.parquet
checks.json
summary.json
report.html
```

Этот CLI-вызов проверяет вычисления, но **не регистрирует запуск в SQLite как пользовательский UI-запуск**. Для просмотра из веб-интерфейса создавайте запуск через конфигурацию, как описано в разделе 2.

## 5. Запуск без Docker (альтернативный способ)

Это способ для разработчиков и экспертов, у которых уже установлены Python **3.11**, Node.js **22** и npm. Данные расположите в `data/` аналогично разделам 2–3.

### Windows (PowerShell)

Проверьте `py --version`, `node --version`, `npm --version`. Скрипт `run.ps1` использует Python Launcher `py` с установленным Python по умолчанию — рекомендуется настроить именно Python 3.11.

Из корня репозитория:

```powershell
powershell -ExecutionPolicy Bypass -File .\run.ps1
```

Скрипт создаст `.venv` (если отсутствует), установит зависимости из `requirements.txt`, запустит FastAPI и Vite. Интерфейс: **http://localhost:5173**; API: **http://127.0.0.1:8000/docs**.

Только API, если нужен без фронтенда:

```powershell
powershell -ExecutionPolicy Bypass -File .\run.ps1 -BackendOnly
```

### Linux / macOS (bash)

```bash
bash ./run.sh
```

Скрипт создаёт виртуальное окружение, устанавливает Python-зависимости, запускает FastAPI и `npm run dev` для фронтенда. Остановка — `Ctrl+C`. Для Linux может потребоваться системный пакет `python3-venv`.

> **Важно:** Docker и локальный запуск используют **разные базы данных**: Docker хранит SQLite в `app_db`, локальный запуск — в `./db/app.db`. Результаты и учётные записи автоматически между ними не синхронизируются.

## 6. Проверки и диагностика

Для запуска Python-тестов **без Docker** после установки зависимостей:

```powershell
# Windows
.\.venv\Scripts\python.exe -m pytest -q tests
```

```bash
# Linux/macOS
./.venv/bin/python -m pytest -q tests
```

Тесты намеренно не включены в Docker-образ бэкенда; для проверки работы контейнера используйте `/healthz`, интерфейс и CLI-прогон из разделов выше.

**Если не открывается интерфейс:** проверьте `docker compose ps`, `docker compose logs --tail=100 frontend` и занятость порта `5173`. Если интерфейс открылся, но нет результатов, проверьте `docker compose logs --tail=100 backend` и правильность `dataset.path`.

**Если ошибка `Dataset path does not exist` или отсутствуют срезы:** проверьте реальную структуру папок и то, что внутри `data/<RUN_ID>/RESULTS/` существуют обе директории `BEFORE_MASTER` и `AFTER_BETA`. В Docker путь определяется **от контейнера**, не от браузера.

**Если ошибка записи `runs/` на Linux:** выполните команду `chown` из раздела 2. При ошибке SQLite убедитесь, что сервис использует Docker volume `app_db`, а не файл из вашей локальной `.venv` или базы Windows.

**Если контейнер не запускается:** проверьте свободные порты `8000`, `5173`, состояние Docker Desktop/Engine и логи. Для пересборки после обновления кода используйте `docker compose up --build -d`.

## 7. Архитектура и структура проекта

| Компонент | Технологии и назначение |
| --- | --- |
| `frontend/` | React 19, TypeScript, Vite; пользовательский веб-интерфейс, сборка в Nginx для Docker Compose |
| `backend/` | Python, FastAPI, SQLAlchemy, SQLite; REST API, конфигурации, запуски, журнал этапов, выдача отчётов |
| `engine/` | Python, pandas, DuckDB, PyArrow, orjson, xmltodict; чтение, нормализация, сравнение, проверки, агрегации и HTML |
| `configs/default_spr.yaml` | Настройка форматов, путей, массивов, атрибутов, проверки и исключения технических полей |
| `procedures/checks/` | Стандартные Python-проверки, исполняемые через интерфейс витрины MartAPI |
| `notebooks/pipeline.ipynb` | Иллюстрация этапов модуля 3 в формате Jupyter |
| `notebooks/demo_data/` | Воспроизводимый малый демонстрационный входной набор (4 пары ответов) |
| `tests/` | Автоматические тесты нормализации, сравнений, платформы, API и отчётов |
| `runs/` | Файлы результатов запусков, созданные локально (не хранятся в Git) |
| `data/` | Входные датасеты, предоставляемые отдельно (не хранятся в Git) |

Поток обработки: **BEFORE/AFTER → чтение JSON/XML → нормализация → сопоставление атрибутов → проверка качества → разрезы и агрегаты → автоматические проверки → сводка → HTML и браузерный отчёт**. Для каждой заявки сохраняется связь с исходными значениями. Ключевые пути и правила сопоставления массивов задаются конфигурацией, а не зашиваются под конкретный запуск.

В локальном режиме запуск выполняется в фоне относительно HTTP-запроса; интерфейс получает статус из API. Для закрытой демонстрации используется вход по имени. **Локальный режим не предназначен для публикации в открытом интернете**: это не полноценная парольная аутентификация. Публичное развёртывание — отдельный сценарий со staging-настройками и защитой доступа (см. `STAGING.md` / `SECURITY.md`). Корневой `Dockerfile` предназначен для staging-сборки; для описанного здесь локального запуска используйте именно `docker compose`.

## 8. Воспроизводимость результатов и замеры

Для корректного сравнения производительности фиксируйте версию исходного кода (`git rev-parse --short HEAD`), число заявок, тип хранилища, модель процессора, объём оперативной памяти и время полного прогона. Фактическое время этапов доступно в журнале запуска. **Аппаратные характеристики ноутбука команды и независимые результаты запуска Docker на чистой машине в репозитории не зафиксированы; здесь они не выдумываются.**

Для приёмки рекомендуется выполнить: запуск на демонаборе, запуск на полном датасете организаторов, проверку 4 типов изменений (`SAME`, `VALUE_CHANGED`, `ATTRIBUTE_NEW`, `ATTRIBUTE_LOST`), переход от сводной до атрибута, открытие результата двумя браузерными сессиями и экспорт HTML. Программа должна вычислять результаты из входных файлов, а не из заранее сохранённых эталонных чисел.
