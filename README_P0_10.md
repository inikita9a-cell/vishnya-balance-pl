# P0-10 — новые структуры и приёмочный прогон

Распаковать весь ZIP в корень репозитория. Патча нет: только новый инструмент,
тесты и эта инструкция. `backend/`, `frontend/`, `data_api.py` и `duck.py` не меняются.

```bash
py -m pytest tests/test_p0_10_acceptance.py -q
py tools/p0_10_acceptance.py --public-dataset data/RUN-20260827-0001
```

Вторая команда предполагает, что это путь именно к исходному открытому набору
2002 пар. Если он лежит в другом месте, заменить путь; пути с пробелами заключать
в кавычки. Настройки читаются из `configs/default_spr.yaml`; другой конфиг можно
передать через `--config`. Пул для полного контрольного прогона выбирается `all`.
Файлы конфига и датасета не редактируются.

Ожидается `22 passed`, затем `PUBLIC` с 2002/502/385 и `P0-10 OK`.
Папка с результатами создаётся каждый раз новая под `runs/p0_10_...`.
В ней: `acceptance.json`, отдельные синтетический и полный прогоны, Parquet и HTML.
Если исходный набор недоступен, можно выполнить команду без `--public-dataset`:
это проверит синтетику, но напечатает `SYNTHETIC ONLY`, а public будет `NOT_RUN`.

## Что проверяется

15 синтетических заявок используют другие имена полей, кириллицу и новые ID.
Это отдельный набор: выданные заказчиком JSON не меняются.

- SAME / VALUE_CHANGED / ATTRIBUTE_NEW / ATTRIBUTE_LOST; изменение данных
  без смены решения; настоящий NULL отличается от отсутствия атрибута.
- Решение DECLINE без причины: заявка сохранена, REASON_AFTER пуст,
  `DECISION_WITHOUT_REASON` указывает на `audit_result.reason`.
- Пропала заявка из BEFORE/AFTER: диагностика `APP_MISSING_*`,
  `COMPARISON_COMPLETE=0`, без выдуманной смены решения.
  Наблюдаемые односторонние строки comparison сохраняются, как в текущем
  контракте; без проверки полноты их нельзя трактовать как подтверждённую
  потерю атрибутов в полной паре. Обычный пропавший атрибут проверяется отдельно.
- Повреждённые JSON/XML и корень-массив: `PARSE_ERROR`, заявка остаётся
  в segments, некорректная пара не публикуется как достоверное сравнение.
- Перестановка четырёх уровней keyed-массивов не даёт ложных изменений.
- Вложенность более 10 сегментов с составными ключами; экранирование `|`, `+`, `%`.
- Модель сравнивается по modelName, числовой вектор — по индексу.
- Дубли ключей, отсутствие ключа и fallback на индекс явно диагностируются.
- Эквивалентные JSON/XML дают одинаковые данные в поддерживаемой схеме:
  NULL, bool, кириллица, строковый код `007`, вложенные массивы.
- Ограничение max_depth не позволяет протащить исключённые поля через сериализацию.
- Повторный прогон даёт те же семь таблиц, источники не меняются.
- CNT факта равен числу distinct APP_ID в fact_apps; summary согласован с segments.

## Полный набор

2002 / 502 / 385 — только явно заданный эталон приёмки исходного набора,
не логика движка и не способ подставить числа в отчёт. Проверка сравнивает
фактические числа и возвращает ненулевой exit code при несовпадении. Дополнительно
проверяются 2002 полные пары файлов, отсутствие пропущенных parse-error заявок,
типы изменений, ключи, связи фактов, сохранность источников и время полного прогона.

Самого полного датасета в переданном проектном ZIP нет; его результат нужно
подтвердить на вашей машине. Новые 22 теста проверены также с принудительной cp1251
для чтений без явной кодировки. Исправлений в движок по этим сценариям не потребовалось.
Отображение диагностики в браузере остаётся отдельной проверкой фронта.
