
Выберите ядро Python из окружения проекта. В архиве уже сохранён вывод успешного
демопрогона. Это **четыре публичные пары**, а не статистика полного датасета.

Для нового расчёта:
1. Найдите ячейку «Параметры запуска».
2. Для demo оставьте DATASET_PATH пустым; для полного датасета задайте:


без редактирования ноутбука используйте команду из следующего раздела.

## Та же проверка без браузера

Скрипт исполняет реальные ячейки из .ipynb в новом процессе IPython, сохраняет
текст и rich outputs в pipeline.executed.ipynb внутри нового запуска. Это удобный
вариант для Windows/CI; второй реализации алгоритмов в скрипте нет.

Демонабор:

```bash
py notebooks/run_notebook.py
```

Ваш полный датасет:

```bash
py notebooks/run_notebook.py --dataset "D:/Destruction/Nuclear Hack/ХАКАТОН_СИСТЕМА_АНАЛИЗА_ИЗМЕНЕНИЙ/ПАКЕТ/ЗАДАНИЕ/data/RUN-20260827-0001"
```

Ожидаемое окончание: `NOTEBOOK OK: <число заявок> applications; pipeline comparison: PASS`.
Каждый вызов создаёт новую папку, имя check_00N подбирать не нужно.
При необходимости: `--config путь.yaml`, `--output-root путь`, `--no-verify`.

VERIFY_PIPELINE=True по умолчанию: датасет считается дважды — сначала по ячейкам,
затем обычным engine.pipeline.run_pipeline для независимой сверки. Время сверки
показывается отдельно. --no-verify полезен для показа уже проверенного сценария,
но тогда статус сверки честно будет SKIPPED.

## Содержимое

| Стадия | Результат |
|---|---|
| s1 | Поиск пар и сирот |
| s2 | Чтение JSON/XML, диагностика ошибок |
| s3 | flatten_pair: общие ключи массивов, пути, глубина |
| s4 | Бакеты без потери исходного VALUE |
| s5–s7 | Union, контроль дублей, четыре CHANGE_TYPE |
| s8–s9 | Качество исходных данных и разрезы по заявкам |
| s10 | Иерархия блоков и доли изменений |
| s11 | Facts и связи FACT_ID → APP_ID; пример точного провала |
| s12 | Пять настоящих CHECK через платформенный subprocess-адаптер |
| s13 | Итоговая сводка и вердикт |
| s14 | Опциональный LLM; по умолчанию пропущен |
| s15 | Существующий самостоятельный HTML-протокол |

У стадий есть пояснение, вход/выход, раскрываемый исходный код из engine,
небольшой вывод, автор/начало/конец и длительность. Для сравнения кода используется
inspect.getsource, копии алгоритмов в ячейках нет.

Сверка сравнивает union, comparison, quality, segments, blocks, facts, fact_apps
целиком. В checks игнорируются DURATION_MS и TRACEBACK (служебные пути в случае
ошибок); ERROR/RESULT и все аналитические поля сравниваются. В summary игнорируются
только run_id и summary_seconds. HTML генерируется той же функцией; байты HTML не
сравниваются, поскольку ссылки содержат разные идентификаторы запусков.

Дополнительные файлы notebook-run:
- notebook_stage_log.json — журнал вызовов стадий;
- notebook_verification.json — итог независимой сверки;
- notebook_execution.json — режим, число заявок и сумма времени стадий;
- pipeline.executed.ipynb — вывод CLI-исполнения (создаётся скриптом).

## Проверка и её границы

В среде подготовки:
- исходный набор: 81 passed;
- выполнены все 20 кодовых ячеек на четырёх публичных парах;
- все семь таблиц, результаты CHECK и summary совпали с обычным пайплайном;
- отдельный тест с пропавшим и повреждённым файлами также прошёл со сверкой;
- итоговый набор: 83 passed.

Проверка выполнена на Python 3.12 через IPython InteractiveShell. Отдельное ядро
Jupyter здесь не смогло открыть локальные сокеты, поэтому интерактивный интерфейс
Jupyter нужно открыть у себя. Тесты не маскируют это как запуск сетевого kernel.
Полных исходных 4004 файлов в архиве не было; полный датасет нужно прогнать
приведённой командой на вашем компьютере. Готовые runs из ZIP не выдаются за
результат нового полного расчёта. Замер четырёх пар не подтверждает SLA полного набора.

Работа с сырыми документами и плоскими строками в разных ячейках увеличивает
потребление памяти относительно потокового исполнения. Показанные времена
исключают отображение результатов и отдельный повторный запуск для сверки.

Ноутбук не создаёт Run в SQLite платформы. Поэтому ссылки из его HTML на API
не будут автоматически доступны как серверный запуск. Для серверного демо
используйте привычный запуск через FastAPI. Pivot/Drill-down UI, Docker и
пользовательский редактор остаются в работе Бэка 2 и фронта.
